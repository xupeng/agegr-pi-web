# PWA install, icons and offline

## "Cannot install this app" is an origin decision, not a manifest one
- `app/manifest.ts` (served at `/manifest.webmanifest`) already provides everything Chrome asks for: `name`, `short_name`, `start_url`, `scope`, `display: "standalone"` and 192px + 512px PNG icons; `app/layout.tsx` links it and adds `appleWebApp` / `themeColor`. Measure before changing any of it.
- Chromium's `Page.getInstallabilityErrors` only covers manifest criteria: it returns an empty list for `http://192.168.11.233:8505/`, which Chrome still refuses to install. The refusal is `not-from-secure-origin` — Chrome installs only from HTTPS or from `localhost` on the device itself. A LAN IP over plain HTTP can never be installed, whatever the manifest says.
- Android does not mint WebAPKs locally: it asks Google's minting service for a token and lets Play install the result, and that service downloads the manifest's **icon URLs** by itself, without credentials. So the icons must be publicly reachable (a LAN/VPN-only origin degrades to a home-screen shortcut), and a reverse proxy that requires auth must leave `/icons/*` reachable. The manifest needs no such exemption — Chrome's manifest fetch reuses the browser's cached HTTP auth entry.
- Verified on a real Android phone (2026-10-09, `e58f996a…`): served over public HTTPS behind Caddy HTTP Basic auth, with `/icons/*` credential-free and the maskable icon in the manifest, Chrome minted a **standalone WebAPK** — the home-screen entry opens with no address bar. That also settles the open question: the minting service did **not** need a credential-free `start_url` (it answers `401` here), so treat the secure origin and the icon reachability as the load-bearing conditions for an authenticated deployment.
- iOS ignores `maskable` and fills transparency with black, which is why the `any` icons stay transparent outside the bubble with an opaque white π (`8c18f21`, after `b315bd3` made them opaque white). Keep that pairing.
- `components/PwaRegistration.tsx` registers `public/sw.js` only in production. This does not prove a reused dev origin has no older registration. Do not unregister all workers or delete origin caches to explain an unverified cache hypothesis.

## Installed iOS header
- In a standalone WebKit app the chat toolbar is an opaque `position: fixed` bar, not sticky. `StandaloneTopBar` keeps a normal-flow slot of `36px + env(safe-area-inset-top)` and syncs the fixed row to that slot's column. Its stylesheet is imported from the root layout, so the first paint is already fixed and opaque; measurement only updates left and width.
- Status-bar style stays `default`, with the explicit `apple-mobile-web-app-capable` tag. `viewport-fit: cover` remains so existing safe-area padding receives insets. Do not add a device-sized top spacer.
- Dropdowns and the inline branch menu stay outside the fixed bar's stacking context. The file tab bar is unchanged. Confirmed on iOS 27.0.1: the header is sharp in normal use and on open.

## The maskable icon contract (`public/icons/icon-512-maskable.png`)
- Android crops `any` icons with its launcher mask. The existing 512 artwork reaches 308.8px from the centre (60% of the width), well outside the 40%-of-width safe circle (204.8px), so it must never be declared `purpose: "maskable"` or `"any maskable"`; a round mask cuts the bubble.
- The dedicated asset scales that artwork to 0.50 about its centre onto a full-bleed `#23454B` plate (the bubble's own colour, so the scaled bubble edge disappears). The mark lands at 154.7px, inside the maskable circle *and* inside Android's stricter 66/108 adaptive-icon zone.
- It is generated once and committed: `.trellis/tasks/10-09-android-pwa-install/research/probes/make-maskable-icon.py`. `plate.paste(mark, box, mark)` is the trap — that mask also blends into the alpha channel and leaves alpha 191..254 edge pixels; use a transparent layer plus `Image.alpha_composite` so the result is fully opaque.
- `public/icons/icons.test.mjs` decodes the PNG itself (no decoder dependency) and asserts 512×512 RGBA, alpha 255 everywhere, no mark pixel outside the safe circle, and the manifest's `maskable` / `any` split. Regenerating the asset means running that test.
- `public/sw.js` precaches only what the page needs offline, so the maskable icon is deliberately not in `PRECACHE_URLS`: the launcher and the minting service fetch it at install time, never the page at runtime.

## Reverse proxies need a Host allow-list entry
- `lib/request-security.ts` trusts only loopback names, IP literals and hostnames configured through `PI_WEB_HOSTNAME` / `PI_WEB_ALLOWED_HOSTS`; every other Host gets `403 Untrusted request` on page *and* API requests. Adding a proxy hostname therefore needs `PI_WEB_ALLOWED_HOSTS` **and a restart**: it is read from `process.env` per request, and a running process cannot be given a new environment.
- Do not substitute a `Host` rewrite in the proxy. `isApiRequestOriginAllowed` compares the browser's `Origin` with the Host-derived request origin, so as soon as the two disagree, requests that carry an `Origin` are rejected and the UI can read but not write.
- Proxy-level HTTP Basic auth is compatible with installation (measured: the manifest fetch reuses the cached auth entry), but its credentials are not persisted across a browser restart, so an installed app may ask for the password again. Cookie-based proxy auth, or Pi Web's own 30-day session cookie, avoids that — and a Basic challenge a standalone app cannot answer turns into a false "offline" launch (see below).

## Authentication and the offline fallback
- `public/sw.js` falls back to `/offline.html` only when a `navigate` request's fetch **rejects**; a `401` response is a successful fetch and never triggers it. A Basic-auth challenge that a standalone web app cannot answer therefore presents as "the app opens offline", not as a login prompt.
- Verified on iOS (2026-10-09): with Caddy HTTP Basic auth in front of the public entry, Safari's "Add to Home Screen" app showed `offline.html` on every launch. The standalone app is a fresh process with no cached HTTP auth credential and no way to show the challenge dialog, so the navigation failed. The same deployment keeps working on Android, where the WebAPK shares Chrome's credential cache — a scheme that is fine in one client can be broken in the other.
- Use Pi Web's own password (`PI_WEB_PASSWORD`) for an app that must work as an installed web app: it authenticates with the 30-day `pi_web_session` cookie, so an unauthenticated navigation gets a normal login page instead. Order matters — the app password must be active first, and the proxy's Basic requirement dropped second, or the entry is briefly unauthenticated.
- The middleware matcher is `["/", "/login", "/api/:path*"]`, so the PWA surface — `/sw.js`, `/offline.html`, `/manifest.webmanifest`, `/icons/*` and `/_next/static/*` — sits outside the password gate on purpose. That is what keeps the service worker registrable, keeps the icons fetchable without credentials for WebAPK minting, and still serves the login page's own JavaScript; `/` and `/api/**` stay gated.
- Offline support therefore does not need an unauthenticated app shell: the shell is gated while everything the service worker precaches is not. Anything that widens the matcher to cover static assets would break installs and offline at once.
