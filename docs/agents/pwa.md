# PWA install, icons and offline

## "Cannot install this app" is an origin decision, not a manifest one
- `app/manifest.ts` (served at `/manifest.webmanifest`) already provides everything Chrome asks for: `name`, `short_name`, `start_url`, `scope`, `display: "standalone"` and 192px + 512px PNG icons; `app/layout.tsx` links it and adds `appleWebApp` / `themeColor`. Measure before changing any of it.
- Chromium's `Page.getInstallabilityErrors` only covers manifest criteria: it returns an empty list for `http://192.168.11.233:8505/`, which Chrome still refuses to install. The refusal is `not-from-secure-origin` — Chrome installs only from HTTPS or from `localhost` on the device itself. A LAN IP over plain HTTP can never be installed, whatever the manifest says.
- Android does not mint WebAPKs locally: it asks Google's minting service for a token and lets Play install the result, and that service downloads the manifest's **icon URLs** by itself, without credentials. So the icons must be publicly reachable (a LAN/VPN-only origin degrades to a home-screen shortcut), and a reverse proxy that requires auth must leave `/icons/*` reachable. The manifest needs no such exemption — Chrome's manifest fetch reuses the browser's cached HTTP auth entry.
- iOS ignores `maskable` and fills transparency with black, which is why the `any` icons stay transparent outside the bubble with an opaque white π (`8c18f21`, after `b315bd3` made them opaque white). Keep that pairing.
- `components/PwaRegistration.tsx` registers `public/sw.js` only in production, so the dev server has no service worker at all. Chrome ≥ 154 does not require one for installability, so its absence explains neither a missing install entry nor a failure.

## The maskable icon contract (`public/icons/icon-512-maskable.png`)
- Android crops `any` icons with its launcher mask. The existing 512 artwork reaches 308.8px from the centre (60% of the width), well outside the 40%-of-width safe circle (204.8px), so it must never be declared `purpose: "maskable"` or `"any maskable"`; a round mask cuts the bubble.
- The dedicated asset scales that artwork to 0.50 about its centre onto a full-bleed `#23454B` plate (the bubble's own colour, so the scaled bubble edge disappears). The mark lands at 154.7px, inside the maskable circle *and* inside Android's stricter 66/108 adaptive-icon zone.
- It is generated once and committed: `.trellis/tasks/10-09-android-pwa-install/research/probes/make-maskable-icon.py`. `plate.paste(mark, box, mark)` is the trap — that mask also blends into the alpha channel and leaves alpha 191..254 edge pixels; use a transparent layer plus `Image.alpha_composite` so the result is fully opaque.
- `public/icons/icons.test.mjs` decodes the PNG itself (no decoder dependency) and asserts 512×512 RGBA, alpha 255 everywhere, no mark pixel outside the safe circle, and the manifest's `maskable` / `any` split. Regenerating the asset means running that test.
- `public/sw.js` precaches only what the page needs offline, so the maskable icon is deliberately not in `PRECACHE_URLS`: the launcher and the minting service fetch it at install time, never the page at runtime.

## Reverse proxies need a Host allow-list entry
- `lib/request-security.ts` trusts only loopback names, IP literals and hostnames configured through `PI_WEB_HOSTNAME` / `PI_WEB_ALLOWED_HOSTS`; every other Host gets `403 Untrusted request` on page *and* API requests. Adding a proxy hostname therefore needs `PI_WEB_ALLOWED_HOSTS` **and a restart**: it is read from `process.env` per request, and a running process cannot be given a new environment.
- Do not substitute a `Host` rewrite in the proxy. `isApiRequestOriginAllowed` compares the browser's `Origin` with the Host-derived request origin, so as soon as the two disagree, requests that carry an `Origin` are rejected and the UI can read but not write.
- Proxy-level HTTP Basic auth is compatible with installation (measured: the manifest fetch reuses the cached auth entry), but its credentials are not persisted across a browser restart, so an installed app may ask for the password again. Cookie-based proxy auth, or Pi Web's own 30-day session cookie, avoids that.
