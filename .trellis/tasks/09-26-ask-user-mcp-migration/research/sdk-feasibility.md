## Concrete server/client/bridge path

- Server: `new McpServer({name,version})`; `registerAppTool(server, "ask-user-view", {inputSchema:z.object(...), _meta:{ui:{resourceUri:"ui://pi-web/ask-user.html",visibility:["app"]}}}, callback)` returning MCP `CallToolResult` with `content:[{type:"text",text:...}]` and bounded `structuredContent` for `{sessionId,askId,...}`. `registerAppResource(server,name,uri,{mimeType:RESOURCE_MIME_TYPE}, () => ({contents:[{uri,mimeType:RESOURCE_MIME_TYPE,text:html}]}))`. The helper also fills deprecated flat URI metadata for compatibility; host should check nested URI against an exact allowlist. It delegates to `server.registerTool`, not to Pi. See [server helper implementation](https://github.com/modelcontextprotocol/ext-apps/blob/v2.0.0/src/server/index.ts).
- **Do not model-call the second tool.** Spec `_meta.ui.visibility:["app"]` hides it from the model while allowing app calls. Trusted host may call read-only projection via its own MCP client (`listTools`, `callTool`, `readResource`); it must never open another ask. Submit/cancel require a separate app-only MCP operation with scoped validation, or a bridge `oncalltool` handler with an exact allowlist. Host must filter the model tool list even if the MCP `tools/list` result includes app-only tools.
- Least-viable local transport candidate: core `InMemoryTransport` paired endpoints connecting v2 `McpServer` and `Client` in the same Node process. Confirm pair factory/constructor and `connect()` order in fixture against pinned package declarations. No HTTP server, stdio child or Pi MCP peer is required for this *Node-side* projection. This is not a browser transport: the browser needs an authenticated, scoped host gateway; never expose a generic MCP endpoint or the in-process client to the iframe.
- [Tagged basic host implementation](https://github.com/modelcontextprotocol/ext-apps/blob/v2.0.0/examples/basic-host/src/implementation.ts): `new AppBridge(client,{name,version},{serverTools:client.getServerCapabilities()?.tools,...},{hostContext:{theme,platform:"web",...}})`; `await bridge.connect(new PostMessageTransport(iframe.contentWindow!,iframe.contentWindow!))`; `await bridge.sendSandboxResourceReady({html,csp,permissions})`; wait for `initialized`; `bridge.sendToolInput({arguments:input})`; `bridge.sendToolResult(result)`. View `new App({name,version},{})`, register `ontoolinput`/`ontoolresult` before `await app.connect()`, call `app.callServerTool({name,arguments})` only for allowed action. Call `bridge.teardownResource({})` before removal, then close bridge and dispose listeners.
- Critical default: [AppBridge.connect](https://github.com/modelcontextprotocol/ext-apps/blob/v2.0.0/src/app-bridge.ts) automatically installs `tools/call` and resources forwarding when given a client with server capabilities; this does **not** enforce per-ask authorization. Use `new AppBridge(null,...)` plus explicit `oncalltool` forwarding only allowlisted names/IDs, or prove equivalent server-side gateway restrictions. `PostMessageTransport` checks `event.source`, but sends with `targetOrigin:"*"`; outer proxy must check source and origin and send to an exact origin ([transport source](https://github.com/modelcontextprotocol/ext-apps/blob/v2.0.0/src/message-transport.ts)).

## Isolation and Pi Web blockers

1. Stable Apps spec requires Host and outer Sandbox to have **different origins**, sandbox permissions `allow-scripts allow-same-origin`, sandbox-ready/resource-ready relay, and inner view with CSP. Tagged [basic host sandbox](https://github.com/modelcontextprotocol/ext-apps/blob/v2.0.0/examples/basic-host/src/sandbox.ts) uses host `localhost:8080` and sandbox `localhost:8081`; [serve.ts](https://github.com/modelcontextprotocol/ext-apps/blob/v2.0.0/examples/basic-host/serve.ts) sets CSP on sandbox HTTP response. A same-origin Next route or directly embedded `srcdoc` is insufficient. Dedicated hostname or isolated port serving *only* the sandbox proxy is plausible; production proxy/LAN/TLS/port choice and cookie behavior remain unverified. Same hostname plus different port separates origins but not cookie scope; never serve host auth cookies or host API on sandbox origin. `allowedDevOrigins` is not iframe isolation.
2. `next.config.ts` has headers only for `/`, `/sw.js`, `/manifest.webmanifest`; `proxy.ts` matches `/`, `/login`, `/api/:path*` with authenticated API admission, and `lib/request-security.ts` checks host and same-origin write origins. `app/api/agent/[id]/route.ts` sends existing `ask_submit` / `ask_cancel` commands through `lib/rpc-manager.ts` and can rehydrate persisted asks. Cross-origin iframe cannot simply fetch the authenticated API; host must mediate and retain auth/CSRF/session admission. A sandbox-serving origin with restrictive CSP is missing deployment infrastructure.
3. `components/ChatWindow.tsx` keys native `AskUserCard` by askId and invokes `submitAsk` / `cancelAsk`; `lib/ask-user/portable/tool.ts` returns `terminate:true`; `lib/rpc-manager.ts` owns store, stale handling and follow-up. Projection must not become authority. Do not send credentials, arbitrary history or unlimited session data in `structuredContent`; server must validate session, askId, open state, stale/duplicate actions and answers on every action.
4. Basic host is reference code, **not a hardened drop-in**: `serve.ts` permits `'unsafe-eval'`, `'unsafe-inline'` and `connect-src 'self'`, and sandbox permits caller-supplied sandbox override. Built-in ask should use fixed URI/HTML, no network domains, server-set CSP (`connect-src 'none'; frame-src 'none'; object-src 'none'`, only necessary bundled script/style), fixed iframe sandbox flags, exact source/origin checking and no permission-policy grants. Validate in a browser. Apps v2 `App` defaults to zod jitless mode for CSP without unsafe-eval ([App source](https://github.com/modelcontextprotocol/ext-apps/blob/v2.0.0/src/app.ts)).
