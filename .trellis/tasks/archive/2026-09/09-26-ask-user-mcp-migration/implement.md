# Implementation plan (awaiting approval)

1. Record pinned Apps/MCP SDK package versions and verify their APIs in an isolated offline fixture. Build a genuine tool/resource/client/view exchange including double-iframe sandbox origin, initialization, tool input/result, scoped answer operation, teardown and text fallback. Store traces and a go/no-go assessment in `research/`. Do not change Pi Web product code until this gate passes; if integration materially changes the approved design, return to planning.
2. Add the smallest local MCP server/client adapter for the built-in ask_user view only. Map the existing open-ask snapshot to a versioned result; retain `askId` as the host authority. Add strict resource identity, size, MIME, CSP and tool-operation admission checks. Do not allow generic tool execution from the iframe.
3. Add a bundled Apps HTML view and isolated sandbox-host wrapper near Pi Web's ask card. Retain native `AskUserCard` as the functional fallback; integrate loading, error, supersede, reload and teardown states in the existing chat flow without changing the Pi tool's model-visible prompt or finish semantics.
4. Exercise submit/cancel against existing server validation and same-session follow-up with offline fixtures. Test races, duplicate/stale IDs, partial/free-text/supplement data, disabled ask_user, persistence/restart and security boundaries. Add browser tests/screenshots at desktop and mobile widths with a nonblank iframe and working inputs.
5. Run `node_modules/.bin/tsc --noEmit`, `npm run lint`, focused ask-user tests, `npm test`, `git diff --check`, plus browser tests. Do **not** run `next build` during dev per AGENTS.md; do not run any real provider conversation. Start/reuse the Pi Web dev server only for the approved implementation/browser phase. Document rollout and fallback results before considering a production switch.

Risky boundary: Pi SDK tool results are not MCP `CallToolResult`, so never assume SDK `details` provide `_meta.ui`. The local MCP adapter must be proved independently. The sandbox origin and host action allowlist are release gates, not styling follow-ups. No PA files, live PA service, `.pi/settings.json` or unrelated planning directories are in scope.
