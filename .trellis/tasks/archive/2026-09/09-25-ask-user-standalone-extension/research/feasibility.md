# Standalone `ask_user` feasibility (SDK 0.85.1)

## Verdict

A reusable Pi tool/core is feasible, but the current inline extension is **not** a drop-in installable question-card feature. `createAskUserToolDefinition()` delegates `open({ sessionId, questions })` to a host callback (`lib/ask-user/tool.ts:106-128`); Pi Web supplies that callback by looking up its live session and throws, rather than returning `terminate: true`, when the session is gone (`lib/ask-user/extension.ts:20-37`). Installing the file in another host cannot supply Pi Web's pending-ask state, answer API, browser UI, or follow-up delivery. A separately installable package must either negotiate an explicit host bridge or fail closed when the bridge is absent. This assessment does not install, publish or run an extension in personal assistant.

## Extraction boundary

| Portable contract | Host-owned behavior |
| --- | --- |
| `questions[]` schema and limits (`lib/ask-user/tool.ts:26-69`, `lib/ask-user/types.ts:16-25`). Validation rules are real but module-private (`lib/ask-user/store.ts:284-376`); a package must export or copy them. `types.ts` also exports the Pi Web-only `pi-web.ask.answers` constant (`lib/ask-user/types.ts:13`), which is not portable. | In-memory one-open-ask lifecycle: open supersedes, and submit/cancel/cancelOpen close it (`lib/ask-user/store.ts:89-140`). Pi Web's wrapper then binds that to session identity, SSE and disk (`lib/rpc-manager.ts:485-507`). A host may reuse the store class; persistence, conversation identity and delivery policy stay host-owned. |
| Tool metadata and `terminate: true` result (`lib/ask-user/tool.ts:106-128`) | Durable pending state, rehydration, state reads and `ask.opened`/`ask.closed` projection (`lib/ask-user/persist.ts:11-28,87-99`, `.trellis/spec/frontend/ask-user-protocol.md`) |
| Pure answer/outcome formatting, already exported and free of framework imports (`lib/ask-user/store.ts:214-232`) | Submit/cancel commands, browser card and cross-device synchronization (`components/AskUserCard.tsx`, `hooks/useAgentSession.ts`, `.trellis/spec/frontend/ask-user-protocol.md`). Pi Web has no ask-specific auth: `/api/*` is gated only when `PI_WEB_PASSWORD` is set (`proxy.ts:27-44`). A host must authenticate submissions itself. |
| Versioned DTOs for open/close/outcome, suitable for a future shared package | Delivering the answer to the correct still-live conversation as a follow-up turn; policy for stop/restart, stale answers and failures (`lib/rpc-manager.ts:518-584`) |

The Pi Web `pi-web.ask.answers` custom message type and its storage filename are application-specific, not a cross-host protocol. Sharing the SDK `defineTool` definition requires an injected `open({ sessionId, questions })` adapter with a clear failure response, not importing Next routes or `globalThis.__piSessions`. A generic CLI/TUI without a persistent host may instead choose a synchronous UI adapter, but that would have different wait and restart semantics and cannot be presented as equivalent to the asynchronous Web form.

## Personal assistant integration path

1. Package the pure schema/tool factory and a small documented `open` bridge contract separately from any Web server implementation. A host adapter must supply its own authenticated open/close/state/answer path. No fallback should return `terminate: true` after failing to register the question.
2. Install only through personal assistant's existing controlled extension mechanism: `$PA_HOME/extensions/` with `ASSISTANT_EXTENSIONS=1` (`src/server/config.ts:81-85,106-108`), or a future explicitly reviewed package loader. Its Stage A admission filters reserved/conflicting/disabled names and only admitted tools contribute prompt hints (`src/assistant/extensions.ts:396-479`); `createRuntime` checks the exact allowlist after binding (`src/assistant/runtime.ts:84-89`). A Pi CLI `pi install npm:<name>` or local-path install is a valid Pi package mechanism (SDK 0.85.1 `docs/packages.md`, Install and Manage), **not** evidence that personal assistant automatically reads the CLI's package settings. Its loader uses isolated in-memory settings with empty `packages` and `extensions` arrays (`src/assistant/extensions.ts:108-117`), turns off SDK package discovery, and loads only `additionalExtensionPaths` built from that fixed directory (`src/assistant/extensions.ts:174-181,212-219`).
3. Make `ask_user` **interactive-only** in personal assistant's host-selected tool set and prompt. Currently the host appends every admitted external name to both interactive and scheduled runs (`src/server/host.ts:983-987`). A scheduled run must continue to use `scheduled_result({status:"needs_input"})` (`src/assistant/extension.ts:221-224`); exposing an asynchronous user wait there conflicts with its terminal-report contract. Filtering after the registered set is known must be done in the host, not by telling the model to ignore the tool. An external extension factory is not given the run origin, so it cannot reliably hide itself.
4. For interactive runs, the host persists pending questions keyed to its conversation identity and exposes the resulting card in its own Web UI. Submissions must be authenticated, validated, idempotent or stale-safe, and delivered to the right conversation without changing the attribution of the human answer. Reconcile state after reconnect/refresh; preserve or explicitly expire unanswered asks on stop/restart. Treat a new ordinary user message as an explicit policy decision for cancelling the previous ask.
5. Preserve existing permissions: an `ask_user` answer supplies missing information only. Personal assistant's `extensionToolGuard` enforces budget, deadline and revocation for external tool calls (`src/assistant/extension.ts:204-214`, installed at `src/assistant/extension.ts:340`); it is not a write-approval gate. Notion save/append require a per-run write permit, and only replace opens a Web confirmation (`src/assistant/extension.ts:280-284`, `src/assistant/operations.ts:62-94`). A checked form option never becomes that permit, a replace confirmation, or a trust bypass.

## Package and failure constraints

- Pi SDK 0.85.1 documents `pi install` for npm, git and local paths (`docs/packages.md`, Install and Manage). Package discovery is a separate contract: `package.json` `pi.extensions` or an `extensions/` convention (`docs/packages.md`, Creating a Pi Package and Package Structure). The tool directly imports `@earendil-works/pi-ai` and `@earendil-works/pi-coding-agent`; those SDK packages belong in `peerDependencies`. Import `typebox` directly only if the package does, and then as a peer too. Other runtime dependencies belong in `dependencies` (`docs/packages.md`, Dependencies). Verify the pinned SDK versions in both hosts (`package.json` in both repositories) when producing a future package.
- Pi Web source is MIT with notice retention for copied substantial code (`LICENSE:1-21`). A future standalone distribution must carry the notice and review its own dependency/asset licenses. Personal assistant has no root `LICENSE` file in the inspected checkout; do not assume it has Pi Web's license.
- Pi Web mirrors open asks best-effort; a write error can lose a card on restart (`lib/ask-user/persist.ts:11-28,87-99`). On close it forgets persisted state before fire-and-forget `sendCustomMessage`; an answer delivery failure is only logged (`lib/rpc-manager.ts:540-563`). This is not an exactly-once delivery guarantee to transfer blindly. Personal assistant must choose and document its own durability and recovery policy before promising an answer was accepted.
- Full system access is granted to installed Pi extension code (`docs/packages.md`, Install and Manage); personal assistant's admission and origin policy are security boundaries, not a sandbox for arbitrary packages. Audit source before installation.

## Follow-up validation matrix (separate implementation task)

- Admission: disabled-by-default, active tool/snippet, rejected reserved/conflicting name, disabled tool, missing bridge fails closed; scheduled run has no `ask_user` tool or hint and still uses `scheduled_result`.
- Lifecycle: open, one pending ask, supersede, submit, skip, cancel, new user message, repeated/stale submission, stop while waiting, server restart and expired/undeliverable answer.
- Web: pending card, refresh, another device, authenticated submit/cancel, error visibility and confirmation that answers reach the intended conversation exactly once or are marked uncertain.
- Permission: user picks a write-looking option; save/append still require the existing per-run write permit, and replace still requires its separate Web confirmation. Prompt injection in question labels/details cannot authorize operations.

## Explicitly deferred

No npm release, Pi package, package API commitment, personal assistant code/UI changes or live end-to-end test are included here. In particular, the host bridge design must be validated with a prototype before claiming cross-host compatibility.
